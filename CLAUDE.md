# Проект «Планёрка» — коммуникационный хаб Генснаб

Ты работаешь над системой, которая собирает всю внутреннюю коммуникацию сотрудников
(планёрки, встречи 1:1, задачи CRM, почту, звонки), превращает договорённости в задачи
с ответственным и сроком, контролирует их выполнение и следит за согласованностью действий.
Подробности — в docs/ (в Claude-проекте — в знаниях): контекст проекта, журнал решений,
«Схема работы помощника» — когда будет получена.

## Главные правила
1. Система не зависит от CRM. Сейчас Битрикс24, далее 1С:Управление торговлей 11.5.
   Источник правды — собственное ядро на сервере компании. CRM — сменный адаптер.
   Любое решение, которое привязывает логику к Битрикс24, — ошибка; вынести в адаптер.
2. Не выдумывать. Ответственного, срок, имя, цифру, статус, возможность API —
   только из источника. Нет данных — оставить поле пустым, пометить и спросить.
3. Задачи из записей и писем не становятся рабочими без подтверждения людьми:
   «на подтверждении» → исполнитель подтверждает → владелец реестра утверждает.
4. Бот пишет только от своего аккаунта, никогда от аккаунта человека.
   Поручения боту (сообщения коллегам, рассылки, посты) — после этапа 7.
5. Во внешний LLM API — только обезличенный текст: ФИО и другие ПДн заменяются
   несклоняемыми токенами ([P7]); таблица соответствий не покидает сервер.
   Обороты, цены, условия поставщиков, названия компаний — не ПДн, не маскируются.
   Исключение — ИП: имя ИП — это ПДн, маскируется.
6. Агент согласованности предупреждает и рекомендует, но задачи сам не меняет.
   Каждое предупреждение, решение человека и итог — в базу опыта.
   Предупреждения и ответы по закрытому источнику или закрытому реестру —
   только тем, у кого есть к ним доступ.
7. Возможности Битрикс24, 1С и ВАТС МегаФон не утверждать по памяти — проверять
   по документации и помечать непроверенное.
8. Claude не распознаёт аудио: распознавание — локальная модель на сервере,
   за интерфейсом (кандидат — GigaAM, запасной вариант — Whisper).
9. Реальные записи, стенограммы, протоколы и справочник — только на сервере.
   В Claude Code и чаты — только обезличенные версии.

## Как работать
- Новая функция или модуль — сначала скилл brainstorming, затем writing-plans;
  код — через test-driven-development.
- Один модуль — одна задача, чёткий интерфейс. Стек: Python, PostgreSQL, Docker Compose.
- Разработчик один, работает через Claude Code — проще значит лучше. Новый сервис
  или библиотеку предлагать только с обоснованием.
- CRM, LLM-провайдер и модель распознавания — сменные адаптеры за интерфейсами.
- Пороги, интервалы, уровни доступа, модели под шаги — настраиваемые параметры,
  не константы в коде.
- Промпты конвейера — отдельные файлы в prompts/ с версиями.
- Решение принято — дописать в журнал решений (docs/).

## Разбор записи встречи
- Имена в тексте уже заменены токенами на сервере. Неоднозначное упоминание
  приходит токеном с кандидатами: [P3|P8] — не выбирать, вынести в вопросы.
- Опираться на итоговую часть встречи (см. «Регламент встреч»). Задачи из обсуждения,
  не повторённые в итогах, — «кандидаты», отдельным списком. Итогового блока нет —
  всё найденное идёт кандидатами, с пометкой «итоги не зафиксированы».
- Поля задачи — по «Схеме работы помощника»: название, ответственный, соисполнители, тип, приоритет,
  цель 2027 (из списка в «Контексте»), срок и контрольная дата (обязательность — по типу),
  критерий готовности, источник (таймкод и цитата), уверенность с причиной, вопросы.
  Неразборчивое — [?]. Ответ — строго по JSON-схеме.
- Изменения по существующим задачам — отдельным списком правок, по номеру И-NNN.
- Новые задачи сверять с активными: на этапе 1 — только пометка в вопросах,
  предупреждения агента — с этапа 4. Типы конфликтов: дубль, противоречие,
  общий ресурс, зависимость, перегрузка, общий клиент, противоречие с данными
  учёта, без реакции. Эталонные случаи — в «Контексте проекта».
