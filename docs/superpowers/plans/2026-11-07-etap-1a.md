## Шапка

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Code — superpowers:test-driven-development.

**Цель.** Запись планёрки, положенная в папку-приёмник, сама проходит путь до утверждённых задач с номерами И-NNN в ядре: распознавание, маскирование ПДн, разбор в LLM, файлы на уточнение исполнителям по почте, утверждение владельцем реестра.

**Архитектура.** Один Python-пакет `planerka`. Распознавание, LLM и почта — модули за интерфейсами, у каждого есть фейк для тестов. Ядро — PostgreSQL. Конвейер — таблица заданий в той же БД и один процесс-воркер, без брокеров и отдельных сервисов. Внешние точки этапа 1а: папка-приёмник, служебный почтовый ящик, Claude API.

**Стек.** Python 3.11, PostgreSQL 16, Docker Compose, SQLAlchemy 2 + Alembic, pydantic 2, pytest, ffmpeg, GigaAM и faster-whisper за общим интерфейсом, anthropic SDK, openpyxl, rapidfuzz, natasha, jiwer. Зачем каждая зависимость — в «Глобальных ограничениях».

**Спека.** `docs/spec.md` — ред. 22 документа «Проект „Планёрка“: инструкция и контекст», выгрузка в Markdown с датой версии. Исполнитель читает спеку и план вместе; при расхождении права спека, а расхождение записывается в журнал решений.

**Рамки.** 21 задача. Этап 1б (встречи 1:1 и видео, закрытые встречи, протокол по «Схеме», мониторинг, отчёт по метрикам) — отдельный план. Сущности этапов 2–5 (CRM, дашборд, конфликты, бот) не создаются.

**Порядок исполнения.** Задачи идут по номерам: каждая опирается на интерфейсы предыдущих (блок «Интерфейсы»). Исключение — задача 11 (сравнение моделей): её можно запускать параллельно с 12–14, как только готова задача 10 и на сервере есть записи 05.11 и 06.11.

## Глобальные ограничения

Каждая задача неявно включает этот раздел. Значения взяты из спеки ред. 22.

- Python 3.11, PostgreSQL 16, Docker Compose. Один модуль — одна задача, чёткий интерфейс.
- Правило 2: ответственного, срок, имя, цифру не выдумывать. Нет данных — поле пустое, флаг, вопрос в поле «вопросы».
- Правило 3: задача становится «в работе» только после двух шагов: исполнитель, затем владелец реестра.
- Правило 5: во внешний LLM уходит только текст, прошедший маскирование и вторую проверку. Токены: сотрудник `[P7]`, неоднозначное упоминание `[P3|P8]`, внешний человек `[X1]`, контакты `[TEL1]`, `[EMAIL1]`, `[INN1]`. Таблица токенов не покидает сервер. Названия компаний, цены, обороты не маскируются; имя ИП маскируется.
- Правило 8: аудио в LLM не уходит. Распознавание — локально, за интерфейсом `Transcriber`.
- Правило 9: в репозитории только синтетические данные. `data/`, `models/`, `reports/`, `backups/`, `.env` — в `.gitignore` с первого коммита.
- Секреты — только в `.env`: `ANTHROPIC_API_KEY`, `HF_TOKEN`, пароли служебного ящика, `BACKUP_PASSPHRASE`.
- Пороги и интервалы — настройки с умолчаниями в `config/defaults.toml`, не константы в коде. Значения с пометкой «старт» — стартовые, правятся в настройках.
- Промпты — файлы `prompts/<имя>.v<N>.md`; версия промпта записывается в результат разбора.
- Статусы задачи: на подтверждении, подтверждена исполнителем, в работе, на паузе, выполнена, снята с повестки, архив, отклонена. Номер — `И-NNN`, не меньше трёх цифр, не переиспользуется.
- В 1а обрабатываются только планёрки; запись встречи 1:1 получает статус «отложено до 1б» (Д-70).
- Тексты для людей (письма, файлы) — по-деловому, коротко, на русском.
- Алерты и логи — без ПДн: номера источников и задач, счётчики, типы ошибок.
- Тесты: распознавание, LLM и почта — фейки. Тесты с настоящими моделями помечены `@pytest.mark.models`, с настоящим ящиком — `@pytest.mark.mail`; оба запускаются только на сервере.
- Решение принято по ходу работы — запись в журнал решений в `docs/spec.md`.

## Review Focus

Пять входов, о которых спека молчит, но которые первыми ударят по людям. Тест на каждый уже добавлен в задачу, которая владеет кодом.

1. **Пауза в записи.** «Звукозапись» на паузе: файл не меняется и уходит в обработку недописанным. Ожидание: если файл изменился после того, как его взяли, старый источник помечается «заменён», новый обрабатывается заново. Задача 8, `test_file_changed_after_ready_is_requeued`.
2. **Файл исполнителя после чужого редактора.** Открыт в LibreOffice или на телефоне: лишние пробелы и другой регистр в «решении», даты текстом, лишний лист. Ожидание: файл принимается или отправитель получает понятный список ошибок; падений нет. Задача 16, `test_parse_tolerates_case_spaces_and_text_dates`.
3. **Имя, которого нет в справочнике.** Уменьшительное вроде «Санёк» или искажённая фамилия. Ожидание: имя замаскировано распознавателем имён, а если нет — вторая проверка блокирует отправку; утечки нет. Задача 13, `test_unlisted_variant_blocks_or_is_masked`.
4. **Относительный срок.** «К следующей среде», «до конца месяца». Ожидание: срок считается от даты встречи, а не от даты обработки; срок раньше даты встречи — поле пустое и вопрос. Задача 15, `test_due_before_meeting_date_flagged`.
5. **Чужие письма в служебном ящике.** Автоответ «в отпуске», ответ без вложения, файл, пересланный с чужого адреса. Ожидание: автоответ игнорируется, без вложения — подсказка отправителю, чужой адрес — отказ; ничего не утверждается. Задача 17, `test_auto_reply_ignored`, `test_reply_without_attachment_gets_hint`, `test_forwarded_from_other_address_rejected`.

### Исполнение

В Claude Code — через superpowers:subagent-driven-development: отдельный исполнитель и отдельный проверяющий на каждую задачу, затем проверка всей ветки.
