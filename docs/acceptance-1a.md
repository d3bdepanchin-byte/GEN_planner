# Приёмка этапа 1а

Чек-лист на сервере с реальными данными. Реальные записи, стенограммы и справочник остаются
на сервере; в репозиторий и чаты — только счётчики и номера. Пункт закрыт, когда «Как проверить»
даёт описанный результат.

## Как запустить

Из каталога проекта на сервере. Секреты — в `.env` (образец — `.env.example`).

1. Собрать образ: `docker compose build` (на сервере по умолчанию `INSTALL_ASR=1`).
2. Поднять БД: `docker compose up -d db`.
3. Миграции: `docker compose run --rm app alembic upgrade head`.
4. Справочник от HR: `docker compose run --rm app planerka import-employees /app/data/staff.xlsx`.
5. Реестр пилота: `docker compose run --rm app planerka import-registry /app/data/registry.xlsx`
   (закрытый реестр — тем же вызовом с `--closed`). Названия колонок — `config/registry_mapping.toml`.
6. Настройки: `docker compose run --rm app planerka setting <ключ> [<значение>]`. Без значения печатает
   текущее (из БД или умолчание), со значением задаёт: число, `true`/`false`, список `"[3, 4]"`,
   иначе строка. Пример: `planerka setting meeting.host_employee_id 12`. Неизвестный ключ — код 2.
   Ключи — в разделе «Данные и настройки».
7. Запустить воркер: `docker compose up -d worker`. Воркер один; второй не запускать.
8. Поставить запись в очередь вручную, если она уже лежит в приёмнике, но не обработана:
   `docker compose run --rm app planerka requeue <номер источника>` (`--as-planerka` — запись без
   фразы открытия разобрать как планёрку).

  Как проверить: `PLANERKA_SAMPLE_WAV=<файл> docker compose run --rm app pytest -m models tests/asr`.

  Как проверить: `docker compose run --rm app pytest -q -W error`, ноль падений и предупреждений.
- [ ] Администратор знает: ошибка конфигурации распознавания (нет библиотеки или модели) —
  вечное ожидание задания с одним алертом на источник, а не остановка. Кто: разработчик.
  Как проверить: в `docker compose logs worker` по этому источнику одна запись об ошибке и один алерт.
- [ ] Воркер один. Кто: сисадмин. Как проверить: `docker compose ps` показывает один контейнер `worker`.

## Бэкапы и эксплуатация

- [ ] `BACKUP_PASSPHRASE` задан в `.env`, копия фразы хранится отдельно от сервера. Кто: сисадмин.
  Как проверить: `planerka backup` не отказывает с «BACKUP_PASSPHRASE не задан».
- [ ] Бэкап создаётся: полный дамп и отдельно таблица токенов, оба зашифрованы. Кто: сисадмин.
  Как проверить: `docker compose run --rm app planerka backup` печатает два пути
  `planerka_<время>.dump.gpg` и `tokens_<время>.dump.gpg`; `head -c 5` файла не `PGDMP`.
- [ ] Проверка восстановления проходит. Кто: сисадмин.
  Как проверить: `docker compose run --rm app planerka restore-check /app/backups/planerka_<время>.dump.gpg`
  печатает число строк по таблицам, `task` совпадает с основной БД. Работает только во
  временную БД `planerka_scratch`: на основную отказывает.
- [ ] Бэкап идёт по расписанию, срок хранения `backup.keep_days` (старт 30 дней, до ответа юриста,
  Д-32). Кто: сисадмин. Строка crontab (путь `/opt/planerka` — пример, подставить свой):
  `15 2 * * * cd /opt/planerka && docker compose run --rm app planerka backup >> /var/log/planerka-backup.log 2>&1`
  Как проверить: в каталоге бэкапов каждый день новая пара файлов, старше срока нет.
- [ ] `BACKUP_DIR` смонтирован с отдельного диска или сетевой папки, не с диска данных. Кто: сисадмин.
  В `docker-compose.yml` сервис `app` монтирует `.:/app`, поэтому `backups/` по умолчанию на одном
  устройстве с `data/`, и `planerka backup` пишет предупреждение «BACKUP_DIR на том же устройстве».
  Пример: `volumes: - /mnt/backup-disk/planerka:/app/backups` у сервисов `app` и `worker`.
  Как проверить: `docker compose run --rm app planerka backup` без этого предупреждения в логе.
- [ ] Копия бэкапов лежит вне сервера (Д-80); её настраивает сисадмин (rsync, облако, второй сервер).
  Кто: сисадмин. Как проверить: файл от сегодняшней даты
  открывается на другом сервере.
- [ ] Внешний мониторинг доступности сервера есть; алерт о падении получают сисадмин и разработчик
  (Д-80). Кто: сисадмин. Как проверить: остановить сервер или отключить сеть на тест, оба получили алерт.
- [ ] Итог задачи 11 (выбор модели распознавания) записан в журнал решений. Кто: разработчик.
  Как проверить: строка в `docs/spec.md`, раздел «Журнал решений».
