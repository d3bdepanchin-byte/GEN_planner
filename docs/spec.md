## Контекст проекта

Собственный хаб на сервере компании собирает всю внутреннюю коммуникацию, превращает договорённости в задачи и контролирует их; CRM и мессенджеры подключаются сменными адаптерами.

### Цель и критерии успеха

Проблема системная: задачи теряются и срывают сроки, информация разбросана по каналам, руководитель не видит статус без ручного опроса, договорённости не фиксируются. Успех:

- договорённость из любого канала становится задачей с ответственным и сроком;
- задача не теряется;
- статус виден на дашборде без опроса;
- вся история задачи — в одном месте.

Главная проблема — несогласованность действий: параллельные задачи, которые дублируют или противоречат друг другу. Отдельный критерий успеха: система замечает такие пересечения и предупреждает до того, как они стоили времени.

Метрики (Д-36). Критерии выше — состояния; измеряем их так:

- доля договорённостей, ставших задачами с ответственным и сроком;
- доля задач с заполненными обязательными для типа полями;
- время от встречи до подтверждённых задач;
- доля и размер просрочек;
- полнота и точность извлечения задач на эталоне;
- доля предупреждений агента, принятых людьми.

База — реестр 05.11, объявленный стартовым: например, у 19 из 62 задач общего реестра не заполнены обязательные для типа поля. С этапа 1а система записывает нужные отметки времени и поля; отчёт по метрикам — позже.

Планёрка руководителей — еженедельно, по средам: 11, 18, 25.11, 02.12 (Д-08). Встречи 1:1 — источник задач наравне с планёрками (Д-04).

Пилот уже идёт: с 05.11 помощник в Claude вручную ведёт протоколы планёрки руководителей по «Схеме работы помощника». Проверяем полноту задач в протоколе, заполнение обязательных полей, подтверждение через файл на уточнение и соблюдение регламента. Окончание — 02.12.2026, после четырёх планёрок. ### Архитектура (подход A: своё ядро + сменные адаптеры)

1. **Адаптеры каналов** — забирают события и доставляют сообщения: записи встреч (аудио и видео в папках встреч на сервере), Битрикс24, почта (IMAP, только чтение), ВАТС МегаФон, позже 1С:УТ 11.5.
2. **Конвейер обработки** — звук из видео (ffmpeg) → локальная модель распознавания за интерфейсом → маскирование ПДн → LLM-адаптер (сейчас Claude API): саммари, кандидаты задач, правки к существующим задачам → расшифровка токенов на сервере (Д-09, 27, 55).
3. **Ядро** — PostgreSQL и правила: статусы, сквозная нумерация задач И-NNN, напоминания, справочник сотрудников с их ID во всех каналах (Д-08, 39).
4. **Выходы** — файл на уточнение по почте (этап 1), дашборд (этап 3), бот в Битрикс24 и окно «спросить агента» в дашборде (этап 5), мессенджер Max (этап 8) (Д-29, 59).
5. **Журнал** — все входящие события и действия системы без изменений.

Отвергнуты: CRM как ядро (при переходе на 1С переделывать всё, история остаётся в Битриксе); low-code n8n (сложную логику трудно поддерживать через Claude Code); MCP-коннектор для Claude в первой версии — всё, что он вернёт, попадёт в контекст Claude с настоящими ФИО, против правила 5 (Д-59). Вернуться к нему после ответа юриста и этапа 3.

### Приём записей встреч (Д-09, 49, 50, 51)

- Записи планёрок: Syncthing отправляет отдельную папку ноутбука в свою подпапку «Записи встреч» на сервере, а не «Звукозаписи» целиком; на ноутбуке тип папки «Send Only», на сервере «Receive Only» — чужие записи на ноутбук не уезжают (Д-69) — там могут быть личные записи. Ведущему ничего делать не нужно; без сети файл уйдёт, когда сеть появится.
- Видео встреч пишется на разные устройства (камера, телефон и др.). Файл кладёт тот, кто записывал, в папку-приёмник «Записи встреч» на сервере: класть в неё может любой сотрудник из офисной сети, читать — только система (Д-69). Звук из видео извлекается ffmpeg.
- У каждой встречи своя папка на сервере: запись, стенограмма, протокол и его версии. Из приёмника система файл копирует, а не переносит (Д-69).
- Файл берётся в обработку, когда его размер не меняется в течение окна стабильности. Окно — настройка: пауза в записи не должна запускать обработку недописанного файла.
- Источник опознаётся по хешу содержимого: повторная доставка не создаёт дублей. Отдельный режим — осознанная переобработка, например после смены модели распознавания; задачи при этом не дублируются.
- Фильтр: в записи нет фразы открытия («Начинаем планёрку» или фразы встречи 1:1) — дальше распознавания файл не идёт, ведущему вопрос. В 1а обрабатываются только планёрки; встречи 1:1 — в 1б (Д-70).
- Телемост: «Звукозапись» пишет с микрофона. Если ведущий в наушниках или встреча полностью удалённая, удалённых участников в записи не будет — проверить на реальной гибридной планёрке.

### Маскирование персональных данных

Во внешний LLM API уходит только обезличенный текст; аудио не уходит вовсе — распознавание работает на сервере.

Как находим ПДн (Д-16):

- Сотрудники — по справочнику всех сотрудников, не только участников встреч: в протоколах есть исполнители, которых на встрече не было. В справочнике — варианты имён (уменьшительные, имя-отчество); сопоставление нечёткое, потому что распознавание искажает фамилии.
- Внешние люди и клиенты — распознаватель имён для русского языка; кандидат — Natasha, проверить на своих текстах.
- Телефоны, e-mail, ИНН — регулярные выражения.

Как заменяем (Д-17, 18):

- Сопоставление имён со справочником — локально, до отправки. Неоднозначное упоминание уходит токеном с кандидатами: \[P3|P8\]; выбирает человек при подтверждении.
- Токены несклоняемые: \[P7\]. Склоняемый псевдоним («Сотруднику7») ломает обратную подстановку и поиск по таблице. Имена в ответе LLM — только в структурированных полях.
- Токен сотрудника постоянный: LLM видит, что \[P7\] в разных встречах — один человек.
- Таблица соответствий «токен ↔ ФИО» хранится только на сервере.

Контроль (Д-19):

- Перед отправкой — вторая, независимая проверка на остатки ПДн. Нет уверенности — текст не отправляется, алерт.
- При расшифровке каждый токен из ответа должен быть в таблице этого источника. Незнакомый токен — поле пустое и помечено.
- Критерий приёмки — ноль утечек на эталоне.

Что не маскируется (Д-21): обороты, цены, условия поставщиков, названия компаний — коммерческая информация, не ПДн. ИП и клиенты — физические лица — это ПДн, маскируются.

Переходный режим (Д-20): пока конвейер не запущен, протоколы делает помощник в Claude по стенограммам. До ответа юриста ФИО в стенограммах перед загрузкой заменяются ролями с номерами: «категорийный менеджер 2», «клиент 1». Правило выполняет автор протоколов (Д-85).

Реальные данные в разработке (Д-22): записи, стенограммы, протоколы и справочник — только на сервере. В Claude Code и чаты проекта — только обезличенные версии.

### Конфиденциальность (Д-04)

- Два признака, оба не зависят от уровней доступа дашборда (Д-71): «источник закрытый» — у встречи и её задач; «реестр: общий / закрытый» — у задачи.
- Встреча 1:1 закрытая по умолчанию; открытой её делает фраза «Встреча открытая» в начале (Д-70). Протокол закрытой встречи получают её участники и владелец реестра. В общий реестр задачи с закрытой встречи идут без цитат и цифр.
- Закрытый реестр — штат, мотивация, зарплаты, оценки людей — ведётся отдельно и в общий реестр не попадает. С планёрки 05.11 в него ушло 7 задач, поэтому признак нужен уже в 1а. LLM предлагает признак по теме, ставит его владелец реестра при утверждении.
- Закрытый реестр видят руководитель компании и владелец реестра; список — настройка. Администратор настраивает систему, но закрытый реестр в дашборде не видит.
- Предупреждения агента и ответы окна «спросить агента», основанные на закрытом источнике или закрытом реестре, получают только те, у кого есть к ним доступ.

### Распознавание речи (Д-24…27)

Модель распознавания стоит за интерфейсом и меняется без переделки конвейера. Кандидат — GigaAM (решение 07.11, предварительное), запасной вариант — Whisper.

О GigaAM — по README репозитория salute-developers/GigaAM, прочитан 07.11.2026, на нашем сервере не проверено: лицензия MIT; нужны Python 3.10+ и ffmpeg; модели — от 220 до 600 млн параметров; у русской линейки v3 есть варианты v3\_e2e\_ctc и v3\_e2e\_rnnt с пунктуацией и нормализацией текста; в обучение добавлены звонки и голосовые сообщения; есть таймкоды слов, экспорт в ONNX и дообучение на своих данных.

Сравнение до выбора (Д-24). Записи планёрки 05.11 и встречи 1:1 06.11 прогоняются через Whisper, v3\_e2e\_rnnt и v3\_e2e\_ctc. Мерим:

- долю ошибок в словах на вычитанном вручную фрагменте 5–10 минут;
- долю верно распознанных фамилий и брендов;
- полноту задач в сравнении с протоколом;
- время обработки часа записи на CPU сервера.

Порог фиксируется до прогона: GigaAM берём, если ошибок в словах не больше, чем у Whisper, фамилий и брендов распознано не меньше, а обработка заканчивается к утру следующего рабочего дня. Сравниваем с вариантом Whisper, который реально работает на нашем CPU (подбираем замером); large-v3 — для справки. Если GigaAM проходит по качеству, но не успевает к утру, — ждём видеокарту или остаёмся на Whisper (Д-82).

Конфигурация (Д-25):

- Метод transcribe работает с аудио до 25 секунд, поэтому для встреч нужен transcribe\_longform с pyannote: токен Hugging Face и принятые условия доступа к pyannote/segmentation-3.0.
- Модели скачиваются заранее; проверить, что конвейер работает без интернета — сервер автономный.
- Берём e2e-варианты: пунктуация нужна маскированию, нормализация — извлечению дат. Есть ли на выходе регистр букв — проверить: без него распознаватель имён работает хуже.
- «Минута записи» в источнике задачи — из сегментов longform или таймкодов слов.

Имена и бренды (Д-26): подсказки списком имён, как initial\_prompt у Whisper, в README нет. Фамилии исправляются сопоставлением со справочником при маскировании. Словарь брендов и поставщиков из учёта передаётся LLM для нормализации — это не ПДн. Не хватит — дообучение на своих записях.

Видеокарта (Д-27): модель должна работать на CPU без урезания; скорость проверяется замером в Д-24. Видеокарта — ускорение (ONNX, onnxruntime-gpu, fp16), а не условие качества. После её установки — включить ускорение и прогнать эталон.

### ВАТС МегаФон: как забирать звонки

Разведка документации 06.11.2026. Два канала, используем оба:

| Способ | Как работает | Роль в системе |
| --- | --- | --- |
| REST API «Другая CRM», команда history | После звонка ВАТС сама шлёт на наш сервер данные звонка и ссылку на запись | Основной: звонок попадает в обработку сразу |
| FTPS-выгрузка записей | Хост records.megapbx.ru, вход логином администратора ВАТС, папки по дням ГГГГ-ММ-ДД | Ежесуточная сверка: догнать то, что не пришло вебхуком |

- REST API и Management API требуют платной опции «Интеграция с CRM» (у компании подключена) — [Management API](http://vats.megafon.ru/management-api).
- Записи хранятся на стороне МегаФона год — [История и запись звонков](http://vats.megafon.ru/history_records).
- В имени файла записи есть имя сотрудника, направление, время и телефон клиента — это ПДн, маскируются до отправки в LLM.
- Звонок обрабатывается один раз по callid — повторная доставка не создаёт дублей.
- Сервер должен быть доступен из интернета по HTTPS, чтобы принимать вебхуки ВАТС.
- Администратор ВАТС определён; учётные данные — вне документов и репозитория.

Поля задачи по «Схеме работы помощника» (Д-01, сверить со Схемой):

- Тип: проект, поручение, регламент, разбирательство. Цель 2027 — одна из: стратегия продаж, сайт и маркетинг, ассортимент, автоматизация и ИИ, эффективность, клиентская база или «нет связи». Список — по протоколам, сверить со «Схемой» или с руководством; хранится как настройка (Д-78).
- Приоритет A/B/C; регламентам не ставится; не больше 5 задач A на человека.
- Обязательные поля по типу (по протоколам): поручению — срок и критерий готовности; проекту и разбирательству — контрольная дата.

**Статусы задачи:** на подтверждении → подтверждена исполнителем (ждёт владельца реестра) → в работе ⇄ на паузе → выполнена. Из любого — «снята с повестки» (можно вернуть) и «архив» (снята окончательно). Кандидат, которого отклонили до утверждения, получает статус «отклонена»: задачей он не стал и хранится как ложное срабатывание для эталона (Д-73).

### Потоки

1. **Планёрка.** Запись → Syncthing копирует файл в папку встречи на сервере → фильтр по фразе открытия → распознавание → маскирование ПДн → LLM: саммари, кандидаты задач, правки к существующим задачам → расшифровка токенов → файл на уточнение исполнителям → исполнитель подтверждает или правит → владелец реестра утверждает → задачи «в работе» в ядре, с номерами И-NNN. Приоритеты утверждаются к следующей планёрке. С этапа 2 подтверждённые задачи создаются в CRM, их ID сохраняются в ядре (Д-02, 06, 49).
2. **Встреча 1:1.** Тот же путь; видео → звук через ffmpeg. Встреча может быть закрытой (Д-04, 09).
3. **Обратная связь.** Комментарии и статусы из CRM приходят вебхуком → история → дашборд. Источник правды — ядро; при конфликте побеждает последнее изменение, в истории видно кто и что.
4. **Напоминания.** До срока, в день срока, при просрочке — с уведомлением руководителя. Интервалы — настройки, значения задаёт руководитель.
5. **Почта и звонки** (этапы 6–7). Договорённости → черновики задач; подтверждает автор письма или участник звонка.

### Подтверждение задач на этапе 1: файл на уточнение (Д-02, 29, 44, 45)

- Роли: ведущий проводит встречу; исполнитель подтверждает, правит или отклоняет своих кандидатов; владелец реестра утверждает и ведёт общий реестр. Сверить со «Схемой работы помощника».
- Файл формирует система. При приёме она проверяет файл и возвращает отправителю ошибки списком. Принимается только .xlsx, только с адреса исполнителя из справочника и только со строками, которые ему отправлены (Д-74). Кандидат без ответственного, с неоднозначным токеном или переназначенный в файле уходит владельцу реестра (Д-72).
- Принятие задачи — подтверждение исполнителя в файле. «Принял» голосом не проверить: распознавание не различает говорящих (Д-45).
- Формат — Excel; у каждого исполнителя свой файл только с его кандидатами (Д-72); колонка «решение» с выпадающим списком («подтверждаю», «правка», «отклоняю»), рядом поле для правки. Файл уходит исполнителю по почте и возвращается на служебный ящик (Д-29).
- Файл не вернулся в срок — напоминание исполнителю, затем владельцу реестра. Отсчёт «без реакции» идёт с момента отправки файла (Д-44, 45).
- После срока кандидат остаётся «на подтверждении», владелец реестра выносит его на ближайшую планёрку; сам по себе он не становится задачей и не удаляется. Срок возврата файла — настройка, стартовое значение — 2 рабочих дня по производственному календарю; календарь нужен уже в 1а (Д-44, 76).
- Служебный почтовый ящик работает с 1а: система отправляет с него файлы, читает ответы, помечает и перекладывает письма. Решение 06.11 «IMAP, только чтение» относится к ящикам сотрудников на этапе 6 (Д-75).
- На этапе 5 файл заменяют дашборд и бот.

### Бот

Имя бота — **Агенснаб** (агент + Генснаб). Вопросы агенту задают в боте Битрикс24 и в окне «спросить агента» в дашборде (этап 5); ответы собирает сервер, в LLM уходит только обезличенный текст.

- Этап 5: отвечает на «мои задачи»; присылает напоминания и предупреждения о конфликтах; в напоминании — быстрые ответы «Принял», «Готово», «Перенести срок». «Перенести срок» — запрос постановщику, а не изменение задачи. Есть ли у бота Битрикс24 кнопки в сообщениях — проверить по документации; если нет — короткие текстовые команды.
- Пишет только от своего аккаунта, никогда от аккаунта человека (Д-58).
- Действия описаны как общие операции; адаптер переводит их в механизмы конкретного канала. Сейчас канал — чат Битрикс24, где идёт вся рабочая переписка; к переходу на 1С — мессенджер Max, затем Telegram. В уведомлениях в мессенджер — минимум данных: номер задачи, название, срок, ссылка на дашборд; без цитат и чужих ФИО.

Поручения боту — после этапа 7 (Д-58): личное сообщение коллеге, групповой чат, рабочая группа или проект, рассылка по отделу, пост в ленту. К потере задач и несогласованности они отношения не имеют, а права и черновики — заметная работа. Решения 03.11 и 06.11 о каналах и правах поручений — отложены. При возврате: черновик → «да» → отправка от аккаунта бота с пометкой «по поручению \[ФИО\]» → запись в историю; права — по уровню доступа: сотрудник — личка и групповой чат; руководитель отдела — плюс рабочая группа и рассылка по отделу; руководство — плюс лента всей компании. Не проверено: может ли бот публиковать в Живую ленту от своего имени.

### Контроль согласованности и база опыта

Старт — на данных, которые уже есть: протоколы планёрок и встреч 1:1. Несогласованности копятся в базе опыта по мере работы (решение 07.11); до этапа 4 — в таблице эталонных случаев (Д-84).

Агент проверяет каждую новую или изменённую задачу против всех активных и предупреждает о конфликте. Задачи сам не меняет — только предупреждает и рекомендует.

| Что ищет | Признак |
| --- | --- |
| Дубль | Одно и то же поставлено разным людям |
| Противоречие | Результат одной задачи отменяет или ломает другую |
| Общий ресурс | Один человек, объект или единица техники нужны двум задачам в одно время |
| Зависимость | Задача не начнётся, пока не закрыта другая, а сроки стоят наоборот |
| Перегрузка | У ответственного на дату больше задач, чем допускает порог (настройка; первый месяц агент только собирает статистику, затем порог ставится по фактической нагрузке) |
| Общий клиент | Несколько сотрудников в один период работают с одним клиентом по разным поводам — предложить один контакт или согласовать очерёдность |
| Противоречие с данными учёта | Задача противоречит статусу клиента в учёте: просроченная дебиторка, суд, стоп-лист |
| Без реакции | Запрос другому сотруднику или отделу не прочитан или не взят в работу за заданное время — напоминание исполнителю, затем его руководителю (время — настройка, сначала сбор статистики) |

Новые типы «нет главного ответственного» и «противоречие с решением», сущность «Конфликт» — в списке доработок, до этапа 4.

Порядок:

1. Находка → предупреждение постановщикам и ответственным через бота и на дашборде.
2. Рекомендация: объединить, перенести срок, сменить ответственного, снять одну из задач.
3. Решение принимает человек.
4. Ситуация, рекомендация, решение и итог записываются в базу опыта.

Как система учится: при новой проверке агент получает похожие прошлые случаи из базы как примеры. Модель не дообучается — улучшение идёт за счёт накопленных случаев. Повторяющуюся закономерность руководитель закрепляет как правило.

### Дашборд

Разрезы: по сотруднику, по статусу, по встрече-источнику, просроченные. С этапа 5 подтверждение кандидатов переходит из файла на уточнение в дашборд и бота; там же окно «спросить агента» — вопросы агенту о задачах своими словами.

Дашборд доступен любому сотруднику — каждый видит свой срез по уровню доступа. Уровни и их состав настраиваются; стартовое предложение:

| Уровень | Видит |
| --- | --- |
| Сотрудник | Свои задачи и где он соисполнитель |
| Руководитель отдела | Задачи отдела и конфликты в нём |
| Руководство | Все задачи общего реестра и все предупреждения; закрытый реестр — по списку доступа (Д-71) |

## Регламент встреч

Правила проговариваются и в начале, и в конце: в начале — кто есть кто, в конце — что решили. Распознавание речи не различает голоса надёжно, поэтому система опирается на произнесённые имена и маркер-фразы, а итоговый блок считается главным.

### Планёрка: открытие (ведущий, 1–2 минуты)

1. «Начинаем планёрку. Дата — \[число\], тема — \[тема\], ведёт — \[Имя Фамилия\]».
2. Каждый участник по кругу, включая подключённых через Телемост: «\[Имя Фамилия\], \[роль\]».
3. Ведущий коротко напоминает правила ниже. Через 2–3 планёрки — одной фразой: «Работаем по регламенту».

### По ходу

- Обращаться по имени и фамилии, не «ты» и «он».
- Говорить по одному.
- Прошлую задачу называть по номеру: «Задача И-021 — …» (Д-08).
- Задачу ставить маркер-фразами:

| Фраза | Что понимает система |
| --- | --- |
| «Ставим задачу: …» | Новая задача, название |
| «Ответственный — \[Имя Фамилия\]» | Один ответственный на задачу |
| «Срок — \[дата\]» | Конкретная дата; «на днях», «скоро» не принимаются |
| «Задача \[номер\] — на паузу» | Статус «на паузе» |
| «… — снимаем с повестки» | Статус «снята с повестки» |
| «… — в архив» | Задача снята окончательно |
| «… — выполнено» | Статус «выполнена» |

### Закрытие (обязательно)

1. Ведущий: «Фиксируем итоги».
2. По каждой новой задаче: «Ставим задачу: \[что\], ответственный — \[Имя Фамилия\], срок — \[дата\]». Ответственный отвечает: «Принял». Номер присваивает система (Д-08).
3. Изменения по прошлым задачам: «Задача И-NNN — \[новый статус или новый срок\]».
4. Ведущий: «Итоги зафиксированы, планёрка закончена».

### Как система это использует

- Задачи и статусы берутся из итогового блока.
- Задачи из обсуждения, не повторённые в итогах, идут отдельным списком «кандидаты».
- «Принял» голосом не проверить: распознавание не различает говорящих. Принятием считается подтверждение исполнителя в файле на уточнение (Д-45).
- Не назван срок — задача помечается в файле на уточнение.
- Нет блока «Фиксируем итоги» — всё найденное идёт кандидатами на подтверждение, ведущему пометка «итоги не зафиксированы» (Д-03).

### Встреча 1:1 — короткий регламент (Д-10)

1. Открытие: «Встреча один на один. Дата — \[число\], участники — \[Имя Фамилия\], \[Имя Фамилия\]».
2. Встреча 1:1 по умолчанию закрытая. Если её можно открыть — сказать в открытии: «Встреча открытая» (Д-04, 70).
3. По ходу — те же маркер-фразы.
4. Закрытие: «Фиксируем итоги»; по каждой задаче — что, ответственный, срок; ответственный: «Принял».
